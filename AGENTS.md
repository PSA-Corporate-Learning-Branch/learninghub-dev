# Repository Guidelines

## Project Structure & Module Organization
The repository stays lean; the rest is generated by Docker at runtime.
- `Dockerfile` builds the WordPress + WP-CLI image with multisite tooling.
- `docker-compose.yaml` orchestrates `wordpress` and `db` services and provisions the `wp_data` and `db_data` named volumes.
- `docker-entrypoint-custom.sh` bootstraps multisite, installs maintained themes/plugins, and applies port-specific patches.
- `README.md` provides onboarding; update it when workflows change.
Generated WordPress files live inside the `wp_data` volume. Use `docker compose exec wordpress ls /var/www/html/wp-content` to inspect themes and plugins.

## Build, Test, and Development Commands
- `docker compose up --build` rebuilds the image and boots the stack.
- `docker compose down -v` resets the environment (removes volumes; run before testing major bootstrap edits).
- `docker compose exec wordpress wp theme list --allow-root` validates theme installs; swap `theme` for `plugin` as needed.
- `docker compose logs -f wordpress` tails the setup script output for debugging.

## Coding Style & Naming Conventions
Shell scripts use Bash with `set -e`; prefer functions for reusable blocks and quote all variables. Keep indentation at two spaces in YAML and four spaces in Bash conditionals to match existing files. Environment variables follow the `WORDPRESS_*` pattern—add new ones in both `docker-compose.yaml` and the entrypoint with uppercase snake case. Commit WordPress tweaks via mu-plugins or themes rather than editing core files directly.

## Testing Guidelines
Treat the bootstrap process as the primary test. After changes run `docker compose down -v && docker compose up --build`, confirm `http://localhost:8181` loads, network sites exist, and `docker compose exec wordpress wp site list --allow-root` shows expected slugs. Use `docker compose exec wordpress wp core verify-checksums --allow-root` after touching core patches to ensure integrity.

## Commit & Pull Request Guidelines
Git history favors short, imperative summaries (`Add multisite patch`, `Fix importer config`). Use the body for rationale and manual steps. For PRs include the purpose, related ticket, any new environment variables, screenshots of the multisite dashboard when UI changes, and confirmation that the bootstrap commands were rerun. Request review from infra whenever Docker or entrypoint logic changes to keep the environment reproducible.
